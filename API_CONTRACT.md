# Tracking Backend API Contract (v0, proposed)

This is the contract the `btp-deploy` CLI expects from the separately hosted SAP CAP
tracking backend. **These endpoints do not exist yet**. This document is the
specification for building them. Nothing in this repository implements the backend
or its HANA schema.

## General

- Base URL: configured on the client (`BTP_TRACKER_API_URL` or `btp-deploy --config`).
  HTTPS is mandatory except for `localhost` during development.
- Requests: `POST`, `Content-Type: application/json`, `Accept: application/json`.
- Authentication: `Authorization: Bearer <token>` (see [SECURITY.md](SECURITY.md)). The
  backend must validate the token. It should derive the **verified caller identity** from
  the token and store that identity separately from the client-reported fields below.
- Successful responses: HTTP `200` or `201` with a JSON body that echoes `deploymentId`.
  The client treats any other body as a failure, including non-JSON, a login page or an
  empty body.
- Errors: non-2xx status, ideally with the standard CAP error body
  `{ "error": { "code": "...", "message": "..." } }`. The client shows `message` (redacted
  and truncated to 200 characters), so it must never contain secrets.
- Client timeout: 15 s by default.

## POST /api/deployments/start

Creates the deployment record with status `STARTED`.

```json
{
  "deploymentId": "6d97c358-fa28-4988-ae1b-b4508643008a",
  "artifactName": "app.mtar",
  "artifactSizeBytes": 10485760,
  "artifactSha256": "73cb3858a687a8494ca3323053016282f3dad39d42cf62ca4e79dda2aac7d9ac",
  "osUsername": "developer",
  "gitUsername": "Developer Name",
  "gitEmail": "developer@example.com",
  "gitRepository": "my-app",
  "gitBranch": "feature/example",
  "gitCommitSha": "0123456789abcdef0123456789abcdef01234567",
  "gitDirty": false,
  "gitLastCommitAuthor": "Developer Name <developer@example.com>",
  "cfApiEndpoint": "https://api.cf.eu10.hana.ondemand.com",
  "cfOrganization": "dev-org",
  "cfSpace": "dev-space",
  "cfUser": "deployer@example.com",
  "clientPlatform": "win32",
  "cliVersion": "0.1.0",
  "startedAt": "2026-10-09T10:15:30.123Z"
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `deploymentId` | UUID string, required | Generated by the client. Primary key. |
| `artifactName`, `artifactSha256`, `artifactSizeBytes` | required | The MTAR itself is never uploaded. |
| `startedAt` | ISO-8601 UTC, required | Client clock. The backend should also store its own receive time. |
| `os*`, `git*` | string, boolean or **null** | Unverified and client-reported. Any of these may be null. |
| `cf*` | string or null | Read from `cf target`. `cfUser` is the CF login, which may be a shared or technical user. |
| `clientPlatform`, `cliVersion` | string | Diagnostic. |

The backend should ignore unknown fields so that newer clients still work.

**Idempotency:** if `deploymentId` already exists with the same content, return `200`
with the existing record. If it exists with different content, return `409`.

Response example: `201 { "deploymentId": "...", "status": "STARTED" }`

## POST /api/deployments/{deploymentId}/finish

Records the result of the deployment.

```json
{
  "deploymentId": "6d97c358-fa28-4988-ae1b-b4508643008a",
  "status": "FAILED",
  "exitCode": 1,
  "completedAt": "2026-10-09T10:17:02.456Z",
  "durationMs": 91833,
  "signal": "SIGINT",
  "errorSummary": "Error: ... (last lines of cf output, redacted, max 2000 chars)"
}
```

| Field | Type | Notes |
| --- | --- | --- |
| `deploymentId` | UUID | Must match the path segment. |
| `status` | `SUCCESS` or `FAILED` | `SUCCESS` only when `cf deploy` exited with code 0. |
| `exitCode` | integer | `cf deploy` exit code. `1` if it was killed by a signal. |
| `completedAt` | ISO-8601 UTC | |
| `durationMs` | integer | Run time of `cf deploy` only. |
| `signal` | string, optional | Present if `cf deploy` was terminated by a signal. |
| `errorSummary` | string, optional | Only on failure. It is redacted client-side, but the backend should treat it as untrusted text. |

**Idempotency:** the client retries finish events that could not be delivered (see the
README section on the retry queue), so the same request may arrive more than once.

- Same result already stored: return `200`.
- Different result already stored: return `409`. The client discards its queued copy.
- Unknown `deploymentId`: return `404`. The client keeps the queued copy and warns.

Response example: `200 { "deploymentId": "...", "status": "FAILED" }`

## Suggested CDS model (non-binding)

```cds
entity Deployments {
  key deploymentId     : UUID;
  status               : String(10);  // STARTED | SUCCESS | FAILED
  artifactName         : String(255);
  artifactSizeBytes    : Integer64;
  artifactSha256       : String(64);
  osUsername           : String(255);
  gitUsername          : String(255);
  gitEmail             : String(255);
  gitRepository        : String(255);
  gitBranch            : String(255);
  gitCommitSha         : String(64);
  gitDirty             : Boolean;
  gitLastCommitAuthor  : String(512);
  cfApiEndpoint        : String(512);
  cfOrganization       : String(255);
  cfSpace              : String(255);
  cfUser               : String(255);
  clientPlatform       : String(20);
  cliVersion           : String(20);
  verifiedCaller       : String(255); // from the validated token, set by the backend
  startedAt            : Timestamp;
  completedAt          : Timestamp;
  durationMs           : Integer64;
  exitCode             : Integer;
  signal               : String(20);
  errorSummary         : String(2000);
  receivedAt           : Timestamp;   // backend clock
}
```

A record that stays `STARTED` indefinitely means one of three things: the client crashed,
the deployment is still running, or the finish event is still queued on the developer's
machine.
